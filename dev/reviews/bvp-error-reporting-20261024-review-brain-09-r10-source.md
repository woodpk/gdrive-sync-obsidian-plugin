## Source-only findings

1. **Ordinary deterministic battery failure now carries an actual diagnostic**. `test-platform/test/batteries/run-deterministic-battery.ts` computes `failed` from nonzero child exit, signal or launch error; normal nonzero exit constructs `deterministic-battery-failed` with phase `test-verdict`, last confirmed `test-subprocess-exited`, first unconfirmed `battery-success-verdict`, unknown effect, next action, bounded hashed run/correlation identity, class `nonzero-test-exit` and a failed exit. Both persisted result JSON and printed safe summary contain the same diagnostic. Launch-error and interruption branches are distinct. The structural TAP projection and stderr suppression remain; original child success/failure status is not silently converted to PASS.
2. **Expected non-success mismatch now has structured scenario/evidence classification**. `test-platform/src/scenario/scenario-runner.ts` calculates `matchedExpectation` from actual step status and declared expectation. When an actually completed step violates an expected failed/blocked outcome, it retains the completed step and constructs `expected-outcome-not-observed`, with phase `expected-outcome-validation`, observed step completion, first unconfirmed expected-outcome confirmation, SHA-derived correlation, step index and safe next action; invokes terminal `finish("failed", ..., diagnostic)`. `scenario-evidence.ts` projects that verdict diagnostic into canonical machine evidence without changing observed step status. This avoids misrepresenting the real step effect or manufacturing an expected failure.
3. **Shared bounded schema**. `test-platform/src/diagnostic-types.ts` and `test-platform/src/live-device/diagnostic-contract.ts` provide classification, component, phase, last/first boundary, effect, recommended action, optional step ID, structured privacy-filtered run/scenario/step/mode/correlation identity, cause class, retriability, and bounded per-hop confidence. Explicit fallback `unavailable`/UNKNOWN values avoid claims of unobserved events. Browser-safe module placement maintains installed validation artifact separation.
4. **Relay and controller error boundaries**. `drive-mailbox.ts` distinguishes malformed outbox/sent records, outbox read, authority, command publication, rename, receipt fetch/write/remove, and polling faults using bounded `unavailable` diagnostic outcomes. `live-scenario-executor.ts` reports local queue, malformed/mismatched receipt and no-response states, without guessing device consumption. `device-command-agent.ts` preserves rejection and uncertain durable sequence/finalization cases. No second orchestration engine or mailbox appears.
5. **Cleanup and entrypoints**. Scenario runner captures disposal errors as separate `cleanupDiagnostic`; completed run with cleanup failure becomes failed, while earlier failed/blocked step reality remains visible. CLI top-level exceptions and result-persistence secondary errors are converted to privacy-safe codes. The physical bridge's outer catch uses safe fixed codes, not raw exceptions.
