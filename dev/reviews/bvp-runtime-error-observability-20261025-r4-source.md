2. **Origin integrity and telemetry:** The journal persists original run/device, validates a bound run's privacy-derived identity when loading, preserves delivery counts and 30s durable retry cooldown, and never guesses a run ID for unbound errors. Device-scoped remote reader compares bound `rawRun` to `opaqueDiagnosticId(rawRun,"run")` in the sanitized diagnostic, and unbound records must have `identity.runId="unavailable"`. 5. **DEC-354 archive operation avoids destruction:** `archiveVerifiedDiagnostic(deviceId,eventId,archiveId)` validates one original ACTIVE source, strict event/route hash and metadata, derives SHA-256 from actual source bytes, creates/reconciles a `diagnostic-archive` record using stable ID, verifies archived media byte equality and archive metadata, rechecks source unchanged, and returns a verified result. 6. **DEC-354 intake gating:** `admitActive(deviceId)` enumerates remote ACTIVE diagnostic objects, including unpublished records, and rejects ambiguous counts/age. ## Frozen independent findings/proof obligations

### R4-S01 — HIGH / architectural acceptance risk — Active-retention lifecycle is not implemented

DEC-354's Option B requires an operational 5000-record / 90-day ACTIVE history, with verified, retrievable archive and retirement only for records proved eligible acknowledged/resolved. In source, `archiveVerifiedDiagnostic` **never deletes or changes ACTIVE source classification**. `cleanup` still deletes only command/result/run-binding, expressly excluding diagnostic. `admitActive` rejects ANY attempt to create a new diagnostic if any ACTIVE record is older than 90 days, but the aged source never becomes non-ACTIVE. Therefore when a device's earliest retained diagnostic crosses the cutoff, every new diagnostic event attempts `admitActive`, sees the same aged ACTIVE file, and aborts; repeated archive copies do not release ACTIVE capacity nor clear age. Similarly, at 5000 ACTIVE records no new events can be admitted even if many are resolved, since there is no approved eligibility/acknowledgment proof and verified retirement workflow. This is **fail-closed and non-destructive**, not false PASS, but falls short of DEC-354's end-to-end retention/archival lifecycle and can suppress future observability indefinitely. Source comments expressly state archival is non-destructive and lacks event-specific resolution. To meet contract, the Owner-approved rules for positive *acknowledged/resolved* eligibility, archive/recheck and conditional safe ACTIVE retirement must be implemented; absent such evidence, preserve original and return explicit BLOCKED, not pretend the 90-day active-history policy is fulfilled. Pass 2 must inspect normative tests of actual safe eligible archive+retire, unresolved protection and resumption of new diagnostic admission after confirmed retirement.

### R4-S02 — HIGH/MODERATE proof obligation — Count/age preflight has no atomic allocation

`admitActive(deviceId)` reads paginated list/count and is followed by an independent metadata `POST` without a per-device reservation or equivalent authoritative atomic quota. Multiple publishers for the same device can both see count 4999 and each create a distinct diagnostic, causing >5000 ACTIVE records, despite both preflight gates having passed. The next publication is refused but does not remove the over-limit state. This matters for the hard active cap even though each device's local journal serializes its own writes; multi-instance restart or concurrent diagnostic processes can race. Pass 2 requires a concurrent two-publisher 4999→5001 adversarial oracle or an explicit fail-closed reconciliation proving no actual over-limit window/continued apparent PASS.

### R4-S03 — MODERATE — Archive proof does not equal acknowledgment or resolution

`archiveVerifiedDiagnostic` cryptographically verifies copy integrity but **does not verify an authoritative per-event acknowledgment/resolved condition**. The relay chooses aged events and archives a copy; it persists a local receipt ID after successful archive, regardless of whether event has been resolved. Because ACTIVE originals remain intact, this is not destructive, but the receipt is not a resolution assertion. Ensure no future change treats successful inbox write, archive verification or local `archivedIds` as authorization to delete protected ACTIVE source. Tests must distinguish acknowledged/resolved versus merely observed, and verify fail-closed when eligibility absent.

### R4-S04 — MODERATE — Cursor and archival durability boundaries

The relay writes one archive receipt list per device and advances the per-device cursor only after a page's inbox records and at most one archived event. Check repeated aged pages, expired cursors, crashed archive create/media/visibility response, archive corruption, archive receipt corruption and restart. Archive is read-only/retention-conservative, but missing or corrupted receipt should not cause source deletion or hidden success.
