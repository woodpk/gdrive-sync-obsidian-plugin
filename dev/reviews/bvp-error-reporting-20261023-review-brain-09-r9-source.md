## Source-only assessment — provisionally conformant; final acceptance reserved for Pass 2

1. **Versioned diagnostic record and privacy**. `test-platform/src/diagnostic-types.ts` defines schemaVersion, classified component, phase, last/first-confirmed boundaries, effect certainty, recommended action, optional step ID, safe identity (run, scenario, step index, execution mode, correlation token), causeClass, retriability and hop status. `test-platform/src/live-device/diagnostic-contract.ts` implements a bounded code allowlist, SHA-derived opaque run/correlation keys, value shape normalization, fallback UNKNOWNs and bounded hop count. This is a substantial direct match to DEC-348's uniform representation and its no-raw-identifiers intent.
2. **Scenario and canonical evidence semantics**. `test-platform/src/scenario/scenario-runner.ts` adds identity-aware step diagnostics, keeps explicit unexpected-effect uncertainty, and captures exceptional disposal as a separate cleanupDiagnostic while preserving the original failed/blocked verdict. Unsupported-mode reports now have structured diagnostics. `scenario-evidence.ts` keeps objective machine assertions and safely projects canonical verdict diagnostic and cleanup diagnostic rather than treating logs as verification authority.
3. **Relay and mailbox**. `test-platform/src/live-device/drive-mailbox.ts` distinguishes malformed outbox/sent command, command read, authorization, publish, rename, result fetch/persist/remove, and converts ordinary errors into bounded `PumpResult` with last/first boundary and UNKNOWN effect. `pollDeviceMailboxOnce` likewise returns a safe unavailable diagnostic on failure. No automatic replay is introduced by diagnostic wrappers.
4. **Device/controller uncertainty**. `live-scenario-executor.ts` preserves distinct outbox write, timeout-with-unobserved-Drive-publication, malformed/integrity-mismatched receipt, and terminal failure classifications. Some hop arrays explicitly mark publication/consumption UNKNOWN rather than presuming delivery. `device-command-agent.ts` sends bounded rejected/uncertain/finalization diagnoses through its existing sequence authority without new transport. Identity tokens are derived from command/run IDs rather than exposed raw.
5. **Entrypoint privacy and result persistence**. `run-deterministic-battery.ts` projects TAP structurally: retains test ordinal, success/failure, counts and timing while dropping raw names, stack frames and child stderr text. `run-live-battery.ts` persists the local result but writes only a safe summary to stdout; CLI exception paths use bounded fail-closed diagnostics and second-order persistence-failure notices. The existing physical bridge's outer exception handler emits fixed-safe classified diagnoses; no new PHX-CI authority or operational BVP gateway.
6. **Architecture separation**. One browser-safe, shared diagnostic contract is accessible without importing scenario orchestration into the installed device build. Existing product src and BVP scenario engines remain separate. Governing DEC-349 changes only 4,000→4,500 and 750→950 logical-line limits; original guard and pinned PHX-CI engineering gate must still be independently verified.

## Source-only risks for adversarial evidence review

- **S9-01, MODERATE / completeness:** Some legitimate early-preflight or remote adapter errors have `identity.runId`, `correlationToken` or step index marked `unavailable`, and the generic default hop list has only two boundary entries. This is acceptable only where those details genuinely cannot be known; Pass 2 must establish sufficiently specific tests of known versus UNKNOWN publication and cause/retriability/identity fields across deterministic, simulated and external-mock paths. The builder must not conflate `unavailable` with demonstrated absence.
- **S9-02, MODERATE / detached subprocess-output fidelity:** `publicTapLine` drops all raw child diagnostics. This appears privacy-safe but can reduce operator detail; Pass 2 must verify failing child TAP is still represented truthfully with accurate test count, exit and bounded actionable diagnosis, including multi-chunk, untrusted-secret cases.
- **S9-03, MODERATE / cleanup:** `safeDispose()` retains cleanup failures even when an earlier step already failed or was blocked, but evidence must prove this does not override the original verdict or manufacture PASS. Evaluate both successful-run finalization failure and prior-failure-plus-cleanup-failure cases.

Such operations remain prohibited. Acceptance can concern only Windows software simulation and mocked integration.
