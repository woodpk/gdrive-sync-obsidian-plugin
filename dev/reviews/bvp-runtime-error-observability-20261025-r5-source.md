## Source-positive observations

Previously problematic coalescing now requires the latest event not be reserved remotely and have `deliveredCount=0`, preserving immutable remote event bytes while keeping subsequent reports pending.
2. **Device never independently activates a new ACTIVE diagnostic.** `publishDiagnostic` creates `brainBvpKind:"diagnostic-pending"` using the durable reserved Drive ID, writes/verifies media, and raises `mailbox-diagnostic-awaiting-controller` rather than returning a false delivered status. `BvpRuntimeErrorJournal.flush` therefore keeps pending until a controller has explicitly promoted the same record and a subsequent device-side publish verifies activation.
3. **Controller-local admission path.** The relay exposes `admitDiagnostic`, checks a controller-authority file with valid generation and uses optional adapter `withExclusiveDiagnosticDevice(deviceId,action)`; the mailbox `controllerOps.admit` validates an immutable pending object, origin/content, age and current global list count before PATCHing kind to ACTIVE, with readback. `pumpCore` promotes at most one staged diagnostic per device cycle. A count/age failure blocks rather than deleting an unresolved entry.
4. **Event-specific acknowledgment and safe retirement.** `acknowledgeDiagnostic(proof)` obtains a controller-specific exclusive adapter operation, verifies the current controller generation, checks exact event/device/run/hash and disposition (`acknowledged`/`resolved`), persists an exact local acknowledgment receipt, then invokes `controllerOps.retire` to independently verify copy SHA/media/metadata, ensure source unchanged and reclassify the original bytes-preserving ACTIVE record as `diagnostic-retired`. Lost response replays reconcile previous retired object only if copy/hash/metadata still match. No direct destructive delete.
5. **Transport and authority separation.** Existing authenticated Drive BVP mailbox is used; historical run and unbound diagnostics are read-only and do not grant command authority. The relay retains bounded 25-entry pages, cursor-expiry recovery and origin-hash validation. Shipping `src/**` is not involved in inspected implementation.

## Source-only findings and proof obligations

### R5-S01 — HIGH/POTENTIALLY BLOCKING: Cross-host unique controller ownership is not established by a *local* OS lock and a locally readable authority file

DEC-356 explicitly demands **one authoritative serialized Windows controller**, rejects competing publishers, and notes that it does not assume an atomic distributed Drive count/lease primitive. `withController()` obtains `adapter.withExclusiveDiagnosticDevice(deviceId,...)`, documented in `RelayAdapter` as **"OS-exclusive, cross-process Windows BVP controller lock"**. Its implementation is a caller-supplied optional adapter method; no concrete native OS lock implementation appears in inspected validation-only `test-platform/src/live-device/**`. That lock, even if correctly implemented on a given Windows host, need not exclude a second host with a separate local lock and locally valid same-device controller-authority record. `controllerAuthority()` validates schema/generation/run/device but does not confirm a globally exclusive authenticated controller lease via Drive. `admitActive()` counts Drive ACTIVE entries and independently PATCHes a pending object to ACTIVE; two separate controllers can both see 4999 and activate different events to reach 5001 despite each local lock. The previously known count race is only resolved when a *single authoritative cross-host owner is actually established*, not merely when each host serializes itself. Also inspect whether a production Windows adapter actually supplies the OS lock; otherwise admission/retirement uniformly fail closed, harming liveness. **Pass 2:** require a test with two disjoint host adapters/locks, same device and controller authority, simultaneous 4999→5001 admission, plus proof of authenticated global singleton/rejection. A conservative fail-closed absence of demonstrated global ownership is preferable to claiming cap enforcement.

### R5-S02 — MODERATE/HIGH: Operator attestation authenticity is implicit, not demonstrated by the proof object

DEC-356 restricts event resolution to an **explicitly authorized Windows controller/operator**, not mere inbox observation or any actor knowing event data. `DiagnosticAttestation` contains schemaVersion, disposition, deviceId, runId, eventId, sha256 and controllerGeneration. `ops.verify()` checks values and matches exact Drive content; `acknowledgeDiagnostic()` verifies the local current generation and local lock. But the proof has **no independently verifiable actor identity, authorization signature or owner/operator approval provenance**. Any caller that can call the exposed `acknowledgeDiagnostic` on a relay object and supply an event's publicly readable content hash and current generation can ask to retire it; there is no separate explicit operator-consent gate visible in these source modules. A trustworthy enclosing Windows operator-only API could establish this boundary, but none was shown in the inspected source. **Pass 2:** identify real caller/adapter authority and tests that a nonoperator/compromised caller cannot turn mere observed diagnostics into a resolved attestation. Otherwise do not treat possession of an event hash as proof of resolution.

### R5-S03 — MODERATE: Controller pending scan and device-side reporting can stall without a bounded global queue contract

`controllerOps.pending(deviceId)` lists up to 25 pending remote records, tests only the first and returns it; there is no pagination/overflow rejection or priority beyond provider listing order, and ACTIVE admission occurs once per relay cycle. Many stalled pending records, an over-age first record or a poisoned first record can prevent later valid pending events from being admitted, preserving them but possibly blocking observability. The default fail-closed limitation must be surfaced and adversarially assessed. Also check crash windows around `diagnostic-pending` visibility and eventual device journal confirmation, without false deliveredCount.

### R5-S04 — MODERATE: Verified byte-preserving reclassification is not the same as unconditional hard ACTIVE capacity under eventual consistency

Even on one host, Drive listing and kind updates are externally consistent only to the extent the authenticated provider guarantees; no atomic conditional update around the observed count is visible. Under stale listing, the controller could promote a new pending entry when the true global ACTIVE count is already 5000. The server-side reservation/lease semantics of any underlying provider must be evidenced or fail closed. `admitActive()` itself rejects 5000 and aged evidence in a clean sequential list; prove exact boundary and ambiguous listing/authorization behavior with adversarial cases.
