## Scope and independent source-only requirement basis

The bounded Step-3 plan calls for an isolated software-only integration of already-existing DEC-339 components: verified Drive metadata baseline, one or more continuous Changes-driven shadow inventory publications, fresh advisory local observation and scope/lifecycle invalidation, canonical cursor/generation atomic publication, and a mandatory deferred **DEC362-14 same-ID continuity demonstration**. Starting with established managed Drive ID A, a content revision must be applied **to A**, observed as an update to A through Google Drive Changes, and persisted in the verified inventory as the *same* A with advanced revision/content evidence. Gaps, identity/fence/pairing/provenance uncertainty, incomplete provider results, stale predecessor and storage/publication failures must fail closed. No inventory-backed planning, deletion authority, live database publication/migration, Drive/vault/device operation, physical testing, master merge or release is permitted.

## What the exact frozen production source establishes

1. **Existing verified reader:** `src/drive/verified-metadata-inventory-reader.ts` `baseline` / `incremental` checks the identity fence, both managed domains and provider-readable roots. `incremental()` starts with the current tracked stable-ID graph, replays Changes by `fileId`, and stores an `upsert` for a changed existing managed ID. It does **not** synthesize a removal/new-ID pair for a normal same-ID revision update. The reader separately validates root-wide marked-object census, affected-parent occupancy, exact identity/provenance, terminal token and fresh fence before returning a candidate. Removed/inaccessible objects do not silently prove deletion.
2. **Shadow publication coordinator:** `src/state/verified-inventory-integration.ts` `VerifiedInventoryBaselineCoordinator.publishBaseline` builds a complete generation from provider observations, validates two-domain coverage and whole graph, stages rows, then invokes guarded atomic publication. `publishIncremental` requires a current active generation whose terminal cursor equals canonical cursor; materializes the pinned verified graph, requests a delta using that predecessor, refuses discontinuous/zero-advance/unbounded observations, reconstructs and validates the whole next graph, and stages only the stable-ID touched overlay records with complete coverage before publishing a durable Changes batch. The code prevents illegal stable-ID domain/kind reclassification.
3. **Atomic storage and restart:** `src/state/indexeddb-inventory-storage.ts` `publishAtomically()` verifies the sealed staged rows and coverage digest, then in one IndexedDB read-write transaction checks the active generation/cursor, authority/fence, domain coverage, stage receipt, persistent authority CAS and learned Changes batch via `prepareInventoryAuthorityPublication()`. Only then does it update the canonical authority bytes, next manifest and active inventory control pointer together. `openRead()` checks canonical/pointer identity and validates the durable generation-chain row count and digests, with pinned read leases. Failed publication is not a trusted inventory. The local snapshot APIs separately require current generation/authority and return advisory, never definitive absence or mutation permission.
4. **Local observation authority separation:** `src/state/verified-local-inventory.ts` keeps its advisory visibility false until fresh complete in-scope enumeration plus durable replacement. File/lifecycle/scope events immediately invalidate, and a rejected IndexedDB invalidation leaves a sticky recovery-required latch until a successful new refresh. Unknown/unreadable local observations are not turned into deletes or BASE authority.
5. **Stable-ID Drive update and shipping boundary:** `src/drive/google-drive-port.ts` includes the same-object `updateExisting` contract, without ordinary predecessor-ID rotation. `src/product/runtime.ts` still constructs the legacy `ProductSnapshotAssembler`; the shadow coordinator is not selected as an execution planner or live authority. This source establishes the isolation boundary but does not itself prove an assembled test actually traverses the mutation→Changes→durable publication chain.

## Blind-source risk checks and qualifications

- **Q-01 — Test-only stage:** The feature is an *assembled software proof*, not new shipping production behavior. Exact source semantics are compatible with the planned proof, but whether a test uses the **real** Drive adapter's same-ID mutation, a matching Changes observation, and durable IndexedDB reopen with positive ID/revision/hash assertions can be determined only after this blind report is frozen and the authored test is opened. A test that merely seeds a desired row or calls the reader directly without observing the update would not satisfy DEC362-14.
- **Q-02 — Non-authoritative shadow:** Canonical cursor/generation is atomically advanced *in the isolated test database* on success. Do not interpret that as permission to write a live paired canonical cursor or to activate the inventory planner; the plan explicitly forbids both.
- **Q-03 — Provider trust:** The code relies on an already-validated root-wide census, changed-parent observations and paired identity fence for a complete incremental horizon; failure statuses must remain fail-closed through the assembled test. Races involving a provider changing *after* its final observation are separately addressed by the existing limited Owner risk decision and cannot be treated as proof of all-world absence.
- **Q-04 — Operational limit:** No software-only test is a substitute for later controlled live schema migration, real device Drive observations, or integrated planner parity. Step 4 remains gated on final independent Step-3 acceptance.
