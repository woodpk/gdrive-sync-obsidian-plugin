## Independent source-only positive observations

1. **Validation-only isolation.** The journal is a browser-safe `test-platform/src/bvp-runtime-error-journal.ts` module, invoked from the separately built validation plugin entrypoint; the production shipping bundle remains intentionally excluded. The Node-only artifact construction is under `test-platform/src/build-validation-artifact.ts` with the historic live-device builder path acting as a forwarding wrapper. No second sync engine or new external broker appears in the code inspected.
2. **Local journal and bounded serializer.** `BvpRuntimeErrorJournal` persists at `<validation-plugin-root>/.bvp-relay/runtime-errors.json`, caps at 24 entries, stores first/last timestamps, occurrence count, `deliveredCount` and outstanding/recovery flag. Serial in-process Promise queue avoids overlapping mutations within one journal instance; overflow is incremented and persisted before an explicit safe-code exception.
3. **Safe diagnostic classification.** Shared `bvpDiagnostic` sanitizes classifications, phases, safe identity tokens, boundaries, effect, recommended action and hop list. The runtime catches transport errors without recording exception bodies or HTTP URLs. The validation plugin's one-second timer invokes `pollAndReportOnce()` and routes unhandled journal failure to a fixed `BVP_RUNTIME_JOURNAL_FAILURE` console code.
4. **Noncommand diagnostic transport.** The mailbox publishes an independent `diagnostic` record kind, initially undiscoverable until upload and metadata publication. The Windows relay retrieves diagnostic records separately from command/results and writes `inbox/bvp-diagnostic-<eventId>.error.json`. It compares occurrence counts before replacing an existing inbox file. Command results and diagnostic records are not conflated.
5. **Recovery/failure honesty.** The journal leaves a failed publish pending by not advancing `deliveredCount`. A successful tick emits a recovery marker only after the existing failure flag; missing/ambiguous poll and relay results do not become command acknowledgments. A safe fallback code exists for failed local journal persistence.

## Independent source-only material findings and proof obligations

### DEC352-S01 — HIGH — Offline pending diagnostic is rebound to the *current* run at flush, losing its originating run/device correlation

**Normative requirement:** DEC-352 requires privacy-safe origin run/device IDs and exact run/device routing and source-origin correlation across offline, restart and delayed delivery.

**Source:** `BvpRuntimeErrorJournal.record(diagnostic)` persists `eventId`, timestamps, counts and `diagnostic` but no explicit immutable origin run/device binding (and no origin run ID in journal `Entry`/`RuntimeErrorRecord`). `installBvpMailboxRuntime()` keeps a mutable `activeRunId` and sets it when `mailbox.activeRun(options.deviceId)` returns a run. On a subsequent tick with **no active run**, `pollCore()` returns `ok` without clearing `activeRunId`. On a subsequent different active run, it replaces the activeRunId. The recovery/flush path uses `mailbox.publishDiagnostic(activeRunId!, options.deviceId, entry)` on *each pending entry* instead of the event's original run. When the originating run is cleared or superseded while offline, pending errors may therefore be published to a stale or new run and displayed under the wrong lease. `unexpected()` creates an identity-less diagnostic for thrown polling/relay exceptions; its run/correlation tokens remain `unavailable`. The journal coalesces equal last diagnoses without binding to the original run, risking conflation across run changes.

**Required:** Bind each event's source run and device (and available command correlation) when recorded using an immutable privacy-safe representation with an authenticated route; preserve it across restart and retry; prevent cross-run coalescing and routing, and distinguish truly unbound events without inventing a run. Reset/reconcile stale active-run state on absence. Verify offline A→B lease transition, no-run transition and restart before final acceptance. No raw identifier leakage.

### DEC352-S02 — HIGH — Remote diagnostic publication is not idempotent under ambiguous response and retry

**Normative requirement:** No duplicate remote writes; safely retry uncertain transport without declaring successful delivery.

**Source:** `createDriveCommandMailbox().publishDiagnostic()` *unconditionally* creates a new Drive metadata file, uploads bytes and publishes discoverability by a final appProperties PATCH. It does not check for an already-published `brainBvpEventId` before a retry and does not use a stable file ID across retry attempts. If the final PATCH succeeded on Drive but its HTTP response was lost, `journal.flush()` retains the pending event; the next retry creates another distinct Drive file for the **same stable eventId**. Windows relay inbox deduplication by eventId does not make the upstream Drive writes idempotent or bound remote growth.

**Required:** Authenticate and locate existing records for the same run/device/eventId before remote creation or establish equivalent idempotent server-side publication semantics. Treat ambiguous creation/upload/visibility as unknown, reconcile before retry, bound duplicates/retention, and test dropped responses at every mutation boundary. Never mark delivery on uncertain response.

### DEC352-S03 — MODERATE — Recovery/transport ordering and stalled pending queues need adversarial proof

**Source:** `tickCore()` on a successful poll flushes all pending errors, adds a `bvp-runtime-poll-recovered` journal record and flushes again. If a diagnostic publication fails, it calls `journal.record(unexpected("drive-mailbox","diagnostic-publication", error))` without an explicit per-event retry cooldown; an equivalent failure can be coalesced each one-second healthy tick while the original event remains pending. A persisted `outstanding` flag does not encode when/from which run the recovery was observed. The 24-record retention limit and overflow behavior must be shown to preserve unresolved failures without false recovery when full. The 1s timer remains best-effort only.

**Required:** Tests must prove bounded retry behavior under lasting outage, no recursive reporting, no fabricated recovery/acknowledgments, correct journal full/corrupt/storage failure fallback, and surviving restart.

### DEC352-S04 — MODERATE — Diagnostic path/metadata trust and terminal persistence deserve focused tests

**Source:** Journal `valid()` checks a limited subset of persisted `diagnostic` fields rather than enforcing the entire reduced safe contract; remote `cleanDiagnostic()` does sanitize and compares full structures, so malicious/tampered journal JSON should fail remote publication, but must be verified without accidentally printing sensitive bytes. `relay` stores events to `inbox/bvp-diagnostic-${eventId}.error.json` using an event ID checked as 36 hex/hyphen characters, and count-based overwrite should not mask conflicting payloads with same event ID. Test that same event ID with differing origin, classification or timestamp is rejected/isolated, not silently considered successful.
