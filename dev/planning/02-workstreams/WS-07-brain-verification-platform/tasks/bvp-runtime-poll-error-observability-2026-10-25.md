## Failure and required outcome
The validation-only plugin's one-second tick currently invokes `pollDeviceOnce().catch(() => undefined)` and the desktop relay equivalent. Typed `status: unavailable` results are also ignored. iOS errors can therefore disappear even with automatic product sync disabled. User requires all BVP errors to be observable, including network/auth/remote result errors.

## Normative contract
1. Replace silent async catch and ignored unavailable results with one stage-specific error boundary. Capture the existing `BvpDiagnostic` classification, stage, confirmed/unconfirmed boundaries, unknown-effect safety and privacy-derived IDs; never capture raw exception text or error stack in persisted or remote evidence.
2. Record a bounded, durable local BVP-only journal under the installed validation plugin's .bvp-relay directory. It must work while offline, coalesce repeated equivalent failures with occurrence counts, preserve first/last occurrence and pending-delivery state across restart, and never touch production managed sync files.
3. When transport is available, publish pending redacted records using the existing authenticated Google Drive BVP mailbox as a separate diagnostic record kind. Never reuse automatic BRAIN sync or command/result records, and never treat a diagnostic delivery failure as a successful command acknowledgment.
4. The Windows relay must collect and durably expose addressed diagnostic records through its existing inbox, idempotently by a stable diagnostic event identifier, preserving exact run/device routing and source-origin correlation; a missing receipt or unknown effect remains BLOCKED/UNKNOWN.
5. A successful poll after failures records the recovery boundary and may retry remote delivery; no uncontrolled infinite retries, unbounded logs, duplicate remote writes or self-recursive reporting.
6. Preserve one-second best-effort foreground polling, iOS background-suspension limits, privacy/identity/lease rules and no change to the shipping plugin. All user-visible logs must be secret-safe; failed journal persistence must emit a safe fallback code and remain an explicit observable blocked condition.
7. Existing three automatic product synchronization options remain OFF for physical readiness; physical test dispatch remains separately gated.

## Mandatory test adequacy and traceability
| Family | Required proof |
| --- | --- |
| Nominal | Successful poll, no false error, delivery of a prior offline failure |
| Negative/malformed | Unavailable result and rejected/invalid diagnostics, storage failure |
| State transitions | Offline -> pending -> delivered -> recovered |
| Idempotency/retry | Duplicate timer ticks and retry do not publish duplicate events |
| Concurrency | Overlapping poll and relay pump cannot race journal flush |
| Persistence | Reconstructed plugin replays the journal; bounded retention |
| Identity/security | Correct device/run correlation; reject raw secrets/invalid tokens |
| Compatibility | Existing result/command semantics and shipping isolation retained |
| Architecture | Existing budget and frozen boundary remain PASS |
| E2E/fail-closed | Failed publication remains pending; unknown effect not turned into PASS |

## DEC-354 Owner Option B — bounded active history and verified preservation (2026-10-25)

The Owner explicitly selected **Option B** after the R3 retention issue: a maximum of **5,000 ACTIVE diagnostic objects per device** and **90 days in active history**, with durable independent archive plus byte-integrity verification **before** eligible active deletion. Never delete unresolved or unacknowledged events; unknown state is unresolved. If protected events prevent the active limit, preserve them and fail closed for additional active publication rather than erase evidence. Existing evidence/archive must remain traceable by opaque event, original device/run, immutable content, and verified archive identity, without exposing raw secrets or turning diagnostics into commands/results.

**Safety architecture:**
- A durable Windows diagnostic-inbox write establishes *receipt*, not an assertion of *resolution*. Neither a successful page fetch nor a `bvp-runtime-poll-recovered` event automatically resolves other events.
- Never delete any ACTIVE remote diagnostic merely because it is old, copied, delivered, counted, or marked recovered. A separate, explicitly trusted event-specific **resolution acknowledgment** must be established before retirement. If that authorization mechanism does not exist, deletion remains blocked and the system must show a typed capacity/retention status.
- Archival must be idempotent over uncertain copy responses and must verify content (and metadata/event identity), restore/reconcile safely across crashes, and preserve an independently accessible archive. The active record must remain until proof of receipt, proof of resolution, proof of archive integrity and stable identity have all been checked. Never infer proof from a single unconfirmed API response.
- Capped list scans, per-operation bounds and 90-day cutoff use trusted Drive metadata and an explicit clock policy. Concurrent remote changes, partial pages, cursor expiry, and repeated pages must not bypass count/age retention.
- The **950-live / 4,550-core** source complexity budgets remain binding; do not add a second protocol, runner or verification authority. Shipping `src/**` remains excluded.
- R3-F01/F03 code and adversarial tests remain **UNQUALIFIED** as of this approval. No new PHX-CI run or Reviewer handoff until the entire authorized retention feature is safely implemented and qualified.

### DEC-354 risk-based test-first acceptance cases (to author as executable tests before production)

1. **Nominal archival:** once an exact event has verified local receipt and explicit trusted event-specific resolution, at the 90-day threshold or active-history overflow, archive the full unchanged redacted payload with exact event/run/device metadata and verify bytes and hash before optional original retirement.
2. **Negative cases:** age threshold -1ms versus boundary, count at 4,999 / 5,000 / 5,001, malformed timestamps, unknown origins, malformed/archive-conflicting metadata, and source hash mismatch MUST not delete any active evidence.
3. **State transitions:** UNKNOWN → RECEIVED → explicitly RESOLVED → ARCHIVED+INTEGRITY_VERIFIED → eligible for ACTIVE retirement; any missing transition blocks retirement.
4. **Idempotence:** transport loses copy/create/verify response after effect, duplicate archival attempts, recovery/restart and partial deletion — one consistent original/archive identity and no false success or wrong-record removal.
5. **Concurrency:** diagnostics may be updated/coalesced while archival occurs; a stale copy must not retire a newer active version; competing history writers and pagination churn must fail closed.
6. **Persistence:** interrupted receipt/attestation/archive state must be durable and replayable, preserving local inbox and original Drive record until independently verified durable copy.
7. **Security:** exact metadata run hash, original device, event ID, privacy-safe archive origin, authenticated existing mailbox and fail-closed rejection of spoofed operator resolution, cross-device approval, and archive copy under wrong scope.
8. **Integration:** no archive query grants historical commands, no production sync, no new OAuth scope/protocol; current diagnostics readers do not mistake archives for fresh active events.
9. **Architecture:** source guard remains hard maximum 4,550 core / 950 live unless Owner separately authorizes amendments; no verification beyond pinned PHX-CI.
10. **Destructive/fail-closed:** remote 503/401/403, returned 400 cursor, copy integrity mismatch, no space, unresolved 90+ day errors and 5,000 unresolved records MUST preserve all existing evidence and report explicit capacity/retention unavailability without new silent deletion.
