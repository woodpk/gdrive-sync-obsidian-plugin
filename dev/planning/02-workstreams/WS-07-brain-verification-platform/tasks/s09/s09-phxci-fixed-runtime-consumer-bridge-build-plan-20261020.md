## 3. Demonstrated fixed-runtime interface

Pinned PHX-CI `schemas/run-request-v1.schema.json` accepts a `focusedTestCommand` string and no physical-run fields. `scripts/common/Invoke-RecordedStage.ps1` captures the command stdout/stderr/exit into a `test-focused` stage record, including nonzero exit. `scripts/common/Write-Evidence.ps1` includes stage `stdout`/`stderr` in the generated evidence JSON. `scripts/Invoke-PhxCiVerification.ps1` publishes its predefined evidence paths through its existing race-protected Git publication. A required stage with exit 3 makes the overall verification BLOCKED, not PASS. This is a candidate *data transport*, not a general-purpose artifact plugin.

**Primary proposed mechanism:** the BRAIN adapter outputs a bounded, privacy-screened, deterministic representation of the **existing** BVP checkpoint/result in PHX-CI's captured focused-stage stdout. PHX-CI thereby records/publishes those exact bytes as part of its ordinary stage record and original evidence. For resume, a BRAIN-side reader uses an exact immutable evidence-commit SHA and the actually published PHX-CI result JSON path to retrieve the prior `test-focused.stdout`; it rejects anything without proof of successful PHX-CI evidence publication. It reconstructs the original BVP checkpoint/result in an isolated approved scratch path and supplies those files to the existing live runner. No new evidence schema family: transport framing carries the existing schema-v2 BVP checkpoint plus existing BVP result.

**Not yet proven:** actual payload size, privacy, executable round-trip through the pinned runtime, retention on a BLOCKED run, and readiness of every listed physical scenario. Failure of any of these is a hard BLOCKED design gate, not a reason to change PHX-CI.

## 4. Identities and immutable authority

Two run identities MUST never be conflated:

- **BVP logical scenario run ID:** stable across separately authorized physical continuation attempts; contains the approved scenario, scenario digest, device map, relay scope, stable validation artifact source identity and actual installed artifact SHA-256.
- **PHX-CI verification run ID:** newly generated by PHX-CI on every invocation, read from its current-run metadata only; never supplied by BVP to PHX-CI or recycled.
- **Attempt index:** monotonic, starting 1, with explicit predecessor evidence-commit SHA, original PHX-CI run ID, actual published history-result JSON path, prior BVP result/checkpoint hash, and previous index. A second attempt cannot begin without a published first attempt.
- **Git source identities:** original BVP validation artifact's source SHA stays fixed; subsequent PHX-CI target HEAD may be a later *evidence-only commit* because PHX-CI itself advances the verification branch when publishing. Before any resume, prove with Git that changes since original source include only allowlisted PHX-CI evidence files, and prove that all relevant product/test/manifest/lockfile/config bytes are unchanged. Any executable or expected-behavior drift is BLOCKED; do not silently rebuild/reinstall or substitute the newer Git HEAD as the device artifact identity.
- **Device/artifact:** derive approved installed `build-identity.json`, `main.js` SHA-256 and `manifest.json` SHA-256 from bounded, authorized nonphysical/physical identity evidence; a sourceCommit string alone is insufficient installation proof.

All evidence-commit ancestry, source-path checks, and published paths must be verified from fetched Git objects. No branch-name-only resume, mutable local-only checkpoint, anonymous stdout marker, fabricated PHX run ID or user-provided claimed PASS qualifies.

## 5. Output transport and parsing contract

Transport is a BRAIN-owned, versioned, bounded line envelope in captured `test-focused.stdout`, not a new BVP evidence verdict. Exact wire grammar and byte limits must be frozen in the first build child before implementation and covered by negative tests. Required logical fields: transport version; BVP ID; PHX-CI run ID; attempt index; BVP battery/scenario identity and digest; approved validation source/build hashes; stable sorted device identity digests; mode (`initial` / `checkpoint-resume` / `verified-late-receipt`); prior evidence commit/path/digest when applicable; original BVP exit code; original machine-readable BVP result encoded without modification; optional original BVP checkpoint JSON encoded without modification; SHA-256/byte length of each payload; privacy/size-check disposition.

Serialize only preapproved *disposable non-secret fixture evidence*. Explicitly scan all data before output, enforce a byte/field allowlist, bound output size, reject duplicate/partial/interleaved envelopes, and cap parsed JSON nesting/array counts. PHX-CI's generic log redaction alone is NOT sufficient. If complete required result or checkpoint cannot be screened and included within approved bounds, return BLOCKED and prohibit resume; do not print raw unreviewed runner JSON. Original BVP CLI may emit full JSON on stdout: capture this in the BRAIN adapter, validate its result file and redaction policy, and emit only approved evidence through the PHX-CI stdout channel. Capture full non-secret command/exit evidence required for accountable analysis. No secrets, note bodies from personal vaults, OAuth materials, account identifiers, or sensitive diagnostic dumps enter Git.

On checkpoint: retain actual BVP exit code 3; PHX-CI's generic focused stage records FAIL (3), and PHX-CI overall records BLOCKED. On completed scenario: BVP exit 0 is eligible for PHX-CI PASS only after all existing gates pass. On exceptions, evidence-validation errors, unexpected output, invalid identities, missing publication, resource limit, or ambiguous receipts: nonzero, not PASS.

## 6. Strict first-attempt and continuation sequence

**A0 — nonphysical preparation.** Use a dedicated BRAIN branch and exact product SHA, controlled run-request with all required ordinary PHX-CI gates. Load only approved public/nonsecret attempt inputs. Verify allowed battery, strictly bounded device/relay paths, test fixture scopes and no current physical execution authorization (the latter means run simulated tests only).

**A1 — initial live attempt (future, separately Owner-approved).** PHX-CI invokes its existing full verifier, whose focused command executes the required deterministic BVP tests **and then** the BRAIN live bridge in the same stage; if deterministic coverage fails, abort before any physical activity. The bridge launches existing BVP CLI and captures verified result/checkpoint evidence. A human checkpoint returns exit 3 without remapping success; no action is prompted inside PHX-CI's noninteractive subprocess. The adapter emits sanitized bounded evidence for PHX-CI capture.

**A2 — publication gate.** The operator must verify that PHX-CI itself produced and durably published the BLOCKED attempt record. The next operator invocation is forbidden if evidence publication failed or output framing is incomplete. Use only the actual PHX-CI-published `result.json` and commit SHA; do not infer that every PHX-CI runtime uses identical paths (the pinned runtime has a different history layout from later development). Treat `dev/_ca-output.json` as mutable current-run convenience, never an immutable predecessor reference.

**A3 — external human action (future approval required).** Outside the noninteractive stage, display the original BVP checkpoint instruction with exact device/action/expected observation/stop condition and separately Owner-approved action budget. Record a sanitized bounded observation note and required BVP evidence tokens. These tokens are assertions of supplied information, not authenticated proof by themselves; the continued BVP scenario must reobserve and assert actual state.

**A4 — fresh PHX-CI invocation.** Create a new PHX-CI verification run. The focused command first retrieves predecessor evidence by immutable Git commit and actual history path; validates source/config ancestry, PHX stage result/exit, BVP transcript version, hashes, scenario digest, device identities, operation budget and authorization. Reject stale, duplicate, conflicting, already-consumed or concurrent attempts. Materialize the exact prior BVP checkpoint/result only inside the permitted scratch area. Run the same scenario with stable BVP ID and approved evidence tokens, continuing only the already-supported BVP path.

**A5 — subsequent checkpoint/completion.** Every new PHX-CI invocation yields its own independently published result. Prior BLOCKED/FAIL data cannot be rewritten. On final scenario completion, full PHX-CI PASS is required; the publication must reference all immutable prior attempts. No BVP success line, independent local result or supplemental late receipt can override PHX-CI status.

## 7. Safety and concurrency invariants

- **Single writer:** only one authorized attempt may own a BVP logical run and its involved device/controller lease at a time. Verify current lease/authority status; fail closed if stale or unverifiable. Crash abandonment is NOT license to delete a lease or redispatch an effect.
- **No automatic replay:** BVP command IDs and device sequence state already provide protections; the adapter must not bypass them or synthesize a success. If a crash occurs after physical effects but before a durable PHX attempt record, stop and reconcile separately. A checkpoint may replay logically completed non-effecting steps, but an uncertain effect cannot be repeated.
- **Resume mode exclusivity:** human checkpoint resume and `--recover-timed-out-result-file` are mutually exclusive. The latter requires original BLOCKED `device-result-unavailable` result and exact correlated late terminal production receipt, with no pending relay queue and only subsequent observe/assert steps. It cannot convert an original BLOCKED run to PASS.
- **No automatic second run on transport failure:** publication failure, cutoff log, worktree cleanup, expired lease, conflicting remote head, missing checkpoint, incompatible schema, unauthorized operation, or failure to bind installed artifact -> BLOCKED; preserve originals and return diagnostics.
- **No mutable public checkpoint authority:** no hidden BRAIN Git evidence publisher, no external backend, no GitHub Actions, no unmanaged personal vault or Drive access.
- **No physical execution without explicit separate Owner approval.** In particular, no S09A rerun, installation, auth, remote root creation, sync, deletion, account mutation or Stage 3.
