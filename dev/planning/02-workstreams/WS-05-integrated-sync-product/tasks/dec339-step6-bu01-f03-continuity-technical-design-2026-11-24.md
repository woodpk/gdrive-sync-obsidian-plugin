## 5. Incremental refresh algorithm

1. Load coherent trusted canonical state/publication and exact lease; validate graph, namespace/coverage and durable authority. Index stable ID, parent→children, normalized occupancy and prior path locally. Never reuse stale lease.
2. Establish fresh pairing and corpus; consume Changes from canonical cursor C (not a new start token), follow complete opaque pagination even empty intermediate pages; unique advancing page tokens, exactly one continuation or terminal, valid IDs/metadata and bounded count/time/retries. Current-state entries may repeat/supersede; conservatively coalesce by ID, preserve old and new affected-scope closure and learned history. Do not assume intermediate events complete. Missing/ambiguous terminal, unknown change type, repeated tokens, failure/cancel/bounds => no publication.
3. Compare changed/new IDs to predecessor. Fresh exact-ID getFile when feed metadata insufficient, unknown provenance/removal/parent; verify changed ancestry to correct domain, cache only same-attempt verified ancestors, require exact marker/root/domain, live kind, one parent, normalized compatible path. Ignore unrelated changes only on affirmative outside-scope evidence. Unknown removed ID, escaped marked object or unclassifiable event => full proof/recovery/block. Do not enumerate foreign/asset trees or fetch their content; if bounded permitted metadata insufficient, block. Never use name to choose identity.
4. Invalidation closure: old/new parent, changed folder/descendants, marker, parent, permission or ownership change, changed root/domain/policy. Ordinary leaf update uses same ID and affected parent occupancy. List affected parent unfiltered, paginated fully, compare actual/candidate ID/name/kind/parent/revision/provenance and duplicate normalized paths. Extra unmarked child, duplicate, missing, inaccessible, revision mismatch, ambiguous subtree or cross-domain/corpus move => no success. F03 may conservatively full rebaseline for folder insertion/move/rename/removal or inherited visibility; never assume unchanged descendants. Avoid querying unaffected remote directories in eligible ordinary path. Deduplicate affected parents/ancestor reads.
5. Removal event, 404/403 or missing metadata is unknown, not deletion. Existing affirmative exact-ID trash proof with known parent/provenance plus trusted history permits existing leaf mask/learned removal semantics; uncertain loss/folder changes rebaseline/block. Preserve ambiguity rather than choose a duplicate name winner.
6. Derive coverage at H from validated complete baseline + complete replay + proven affected scopes; no pretending inherited rows were freshly listed. Explicit proof basis distinguishes inherited continuity from fresh targeted evidence; if current contract cannot distinguish, extend compatibly or retain census. Validate entire local effective graph/ambiguity/digests/bounds. Independently verify final fence and horizon AFTER last provider read; if H drifted discard staging and boundedly retry/replan. Do not rewrite BASE from inventory.
